# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

nopCommerce 5.00 (ASP.NET Core, .NET 10, `net10.0`, SDK pinned in `global.json`). Solution is `src/NopCommerce.sln`. Main branch is `develop`; commit subjects reference the tracker issue number (e.g. `#8102 ...`).

## Commands

```powershell
dotnet restore src
dotnet build src/NopCommerce.sln -c Release
dotnet test src -c Release                                   # NUnit, whole suite
dotnet test src --filter "FullyQualifiedName~ProductServiceTests"
dotnet test src --filter "Name=CanParseProductAttributes"
dotnet run --project src/Presentation/Nop.Web --urls http://nomo.local:5000   # always nomo.local, never localhost (see below); first run shows the installation wizard
```

Always browse the local store at **`http://nomo.local:5000`**, never `localhost:5000` — `nomo.local` is the store URL in the `Store` table, and the NopStation plugin licenses are domain-bound, so their widgets silently render nothing on `localhost`.

Client-side libraries (jQuery, AdminLTE, bootstrap, CLDR data) are copied into `wwwroot/lib` by gulp, not committed:

```powershell
cd src/Presentation/Nop.Web; npm install; npx gulp
```

CI (`.github/workflows/dotnet.yml`) runs restore → build → test on `develop` pushes/PRs. Docker: `docker compose up` (root `Dockerfile` builds and publishes `Nop.Web`).

There is no lint step — style is enforced by `.editorconfig` (warnings, not errors).

## Local state that is gitignored

`src/Presentation/Nop.Web/App_Data/{appsettings.json,dataSettings.json,installedPlugins.json}` are generated by the installer, and `src/Presentation/Nop.Web/Plugins/*` is build output. Never commit these; never assume they exist when reading config — `Program.cs` adds `appsettings.json` as optional and `DataSettingsManager.IsDatabaseInstalled()` gates everything that touches the DB.

## Architecture

Layers, strictly one-directional: `Nop.Core` (domain entities, settings, caching primitives, engine) → `Nop.Data` (LinqToDB + FluentMigrator) → `Nop.Services` (business logic) → `Nop.Web.Framework` (MVC infrastructure, DI composition root) → `Nop.Web` (public store + `Areas/Admin`) → `Plugins/*` (reference `Nop.Web`).

### Composition by convention, not by explicit wiring

`NopEngine` scans all loaded assemblies via `ITypeFinder` and instantiates everything it finds, ordered by an `Order` property:

- `INopStartup` — service registration + middleware. The big one is `Nop.Web.Framework/Infrastructure/NopStartup.cs`; **every new service interface must be registered there** (or in a plugin's own `PluginNopStartup`).
- `IStartupTask` — runs even for uninstalled plugins (needed so plugin installation can work).
- `IConsumer<T>` (`Nop.Services.Events`) — event handlers, auto-discovered. `IEventPublisher.PublishAsync` fans out to them.
- `IOrderedMapperProfile` — AutoMapper profiles.
- `IRouteProvider` — endpoint registration (plugins add their routes here).

Consequence: adding a class is often the whole wiring step. Conversely, a plugin DLL missing from `Nop.Web/Plugins/` means none of its types are discovered.

### Data access

LinqToDB, **not** Entity Framework. `IRepository<TEntity>` is the only data entry point services use; it takes a `Func<ICacheKeyService, CacheKey>` so caching is opt-in per call. Table/column mapping lives in `Nop.Data/Mapping/Builders/**` (`NopEntityBuilder<T>`), with legacy name overrides in `BaseNameCompatibility`.

Schema is owned by FluentMigrator, versioned by timestamp attributes:

- `[NopSchemaMigration("yyyy-MM-dd HH:mm:ss", "...")]` — DDL, in `Nop.Data/Migrations/UpgradeToXXX/SchemaMigration.cs`, always guarded by `Schema.Table(...).Column(...).Exists()`.
- `[NopUpdateMigration(date, "5.00", UpdateMigrationType.Localization|Settings|Data)]` — locale resources and settings live in `Nop.Web.Framework/Migrations/UpgradeToXXX/` (they need service-layer types).
- `[NopMigration(date, ..., MigrationProcessType.Update)]` — pseudo-migrations that mutate `appsettings.json` etc.

Migrations are `ForwardOnlyMigration` / `MigrationBase` and must be idempotent. Supported providers: MS SQL, PostgreSQL, MySQL (`Nop.Data/DataProviders/`).

### Caching

`IStaticCacheManager` (memory / Redis / SQL Server / synchronized-memory, chosen from `DistributedCacheConfig`) plus `IShortTermCacheManager` (per-request). Cache keys are `CacheKey` objects with prefixes declared in `*Defaults` classes. Invalidation is event-driven: `CacheEventConsumer<T>` subclasses in `Nop.Services/**/Caching/` react to `Entity{Inserted,Updated,Deleted}Event`. When you add a cached query, add the matching consumer or the cache goes stale.

### Presentation

Controllers stay thin: they resolve permissions, call services, and delegate all view-model building to an `I*ModelFactory` (`Nop.Web/Factories/` for the store, `Nop.Web/Areas/Admin/Factories/` for admin). Cross-cutting behavior is action filters in `Nop.Web.Framework/Mvc/Filters/` (`[CheckPermission(StandardPermission.…)]`, `[AutoValidation]`, `[CheckAccessPublicStore]`, …). Views resolve through `ThemeableViewLocationExpander` so themes (`Nop.Web/Themes/DefaultClean`) and plugins can override them. Bundling is WebOptimizer (`Nop.Web.Framework/WebOptimizer`).

Admin lives in the `Admin` area with its own controllers/factories/models/validators — keep admin and public concerns in their respective trees.

### Plugins

Each plugin is a self-contained project with `plugin.json` (SystemName, Version, `SupportedVersions`, FileName) and `OutputPath` pointed at `$(SolutionDir)\Presentation\Nop.Web\Plugins\<SystemName>`. Key rules:

- Plugins reference `Nop.Web`; `Nop.Web` never references plugins.
- `CopyLocalLockFileAssemblies` is `false` unless the plugin pulls its own NuGet packages, and the post-build `ClearPluginAssemblies` target strips duplicated framework DLLs from the plugin output.
- `BasePlugin.InstallAsync/UninstallAsync` add and remove settings and locale resources (`AddOrUpdateLocaleResourceAsync`) — uninstall must undo exactly what install added.
- Plugin-owned tables get their own `Data/Mapping` builders and `Data/Migrations`.

## Tests

`src/Tests/Nop.Tests` — NUnit 4 + Moq + AwesomeAssertions (the FluentAssertions fork; `using AwesomeAssertions;`). `BaseNopTest` boots a full DI container against a **SQLite** file provider and runs a real install with sample data; `ServiceTest` additionally initializes plugins. Because that install is shared across the run, tests mutate seeded data (product id 1, etc.) — write tests that tolerate existing rows and clean up what they insert. Mirror the source tree: `Nop.Tests/Nop.Services.Tests/<Area>/<Type>Tests.cs`.

## Conventions

- Everything is `async` and suffixed `Async`; there are no sync service methods to fall back on.
- Classes and interfaces are declared `partial` throughout (so integrators can extend without forking) — follow that.
- Injected dependencies are `protected readonly` fields prefixed `_`, listed alphabetically, inside `#region Fields` / `#region Ctor` / `#region Methods` / `#region Properties`.
- File-scoped namespaces, `System` usings first, UTF-8 **with BOM**, no final newline (`.editorconfig`), 4-space C# indent, 2-space for csproj/json/js/css.
- Controller actions are `public virtual`.
- User-facing strings are never literals — add locale resources (`defaultResources.nopres.xml` for new installs, a `LocalizationMigration` for upgrades) and read them via `ILocalizationService`.
- New admin functionality needs a `StandardPermission` entry and a `[CheckPermission]` on the action.
